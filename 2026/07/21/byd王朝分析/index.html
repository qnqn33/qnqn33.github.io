frida检测绕过

1.内容过滤

sub_338A0 是 JNI_OnLoad 里调用的第一个检测函数

就是检测虚拟文件的名字里面是不是有frida的关键词
应对:

先在onEnter检查每次调用fopen的时候第一个参数有没有maps, 如果有大概率就是frida检测这里调用的,把它标记一下. 然后在onLeave的时候放到mapsFiles对象里面, 作为后续 fgets hook 的判断依据, 不然其他地方调用fgets的时候也会经过一次判断, 不仅吃性能, 还存在误伤的可能.

onEnter 保存 fgets 的三个参数中的两个a[0] 是目标缓冲区指针(fgets 会把读到的行写进这里),a[2] 是 FILE* 指针. onLeave 先检查这个 FILE* 是不是上一步标记过的 maps 文件，如果不是就完全不管。如果是 maps 文件，读缓冲区里 fgets 刚写入的那一行，转小写后遍历关键词列表。命中了就用 writeUtf8String 把缓冲区内容替换成 "00000000-00000000 --- 0 00:00 0\n" ——一个格式合法但不含任何关键词的假行. 然后strstr就不会检测出来.

除了这个以外, JNI_OnLoad 里还有 sub_41CD0 / sub_576B4 / sub_8C1E4 三个函数用 SVC openat + SVC read 直接发系统调用读 map, 完全绕过libc. 那这个部分我是通过kpm模块去hook, show_map_vma在内核层面把frida的vma条目隐藏.

拦截退出

这个非常明确, 程序后面还是有检测到有异常, 不过是程序正常退出, 不是我之前观察到的引导到错误地址直接崩溃, 所以把正常退出路径给拦截了.

线程检测

检查 this.p（onEnter 保存的路径）是否含 “DexHelper”. 如果是，通过 Process.findModuleByName 拿到 SO 在内存中的基地址. patched 标志确保只执行一次.

检测线程发现 Frida 后不走 libc 的 kill/exit（已经被我们 replace 了），而是直接用 SVC 指令发起内核系统调用：

ai用 IDA py 脚本 对 dump 出来的 SO 自动扫描。脚本遍历所有可执行段找 SVC #0 指令，回溯 X8 寄存器的赋值指令确定 syscall 编号，过滤出 __NR_kill(129) / __NR_exit(93) / __NR_exit_group(94) 等退出类调用，自动输出偏移列表。这个 SO 里扫到 109 条 SVC 指令，其中 6 条是 kill。

把每条 SVC 0 指令（4 字节）替换为 NOP（0xD503201F）。CPU 执行到这里时跳过不做任何事，后面的错误检查代码 CMN X0, #0xFFF; B.CC ... 会认为 syscall 返回了 0，程序正常继续。

wbenckeys 和 iv
两层laes用的key是硬编码在字符串常量里的, 每个488字符, 一眼看过去像随机hex, 其实是白盒AES的查找表参数. dump出来分别叫WBENC_KEY0和WBENC_KEY1, 直接原样存到Python常量里就行, 完全不用理解里面是啥.

第一层iv叫StrIv1, 16字符, 每次随机生成, 字符从一个固定字母表里选:

这个字母表就是普通ASCII, 但顺序被打乱, 从字节层面看没有规律. 生成时机是getRandomString(16).

第二层iv是完全固定的:

硬编码, 直接抄.

Nd.a 的三个预处理函数
这里是最抽象的部分. Nd.a有三个方法, 名字都带160: preDataIn160 / preDataOut160 / preIv160. 反编译出来大概是这样:

((b & 0x55) << 1) | ((b & 0xAA) >> 1)这个操作叫swap adjacent bits, 就是把每对相邻的比特两两互换, 一个字节的8个bit重新洗牌. 数学上等价于一个特殊的置换, 输入输出一一对应, 而且自身是可逆的(做两次等于原值).
preDataIn比另外两个多一步^0x44, 因为输入还需要再打乱一次. preDataOut和preIv一样. 说白了就是加固sdk自己给laes的输入/输出/iv套了一层混淆, 阻止你直接看内存里的原始明文密文.

CryptoTool.laesEncryptByteArr
到这里就没Java代码可以看了, CryptoTool加载的是libwbsk_crypto_tool.so, 白盒AES实现完全在native里. 白盒AES的特点是把key直接烧进查找表, 光看so拿不出真key, 只能整体当黑盒用.
自己重写这个native的成本非常高, 一般白盒AES论文里的算法都有各家自己的私货, 逆一个月都不一定搞得对. 我这里的做法是用unidbg把这个so加载起来, 起个http服务, python这边POST arg0/arg1/arg2过去, 拿返回值. 相当于所有加密操作都在unidbg里跑, python只负责组织数据.

所有登录相关的加密逻辑全部还原完了. 主dex里的公共网络层还看到过一些K3/K6/ParamsUtils2的调用, 一开始不确定是不是和登录有关, 也顺手看了一下.

复现登录: token.js + login.py

复现分两步. 一个是运行时拿到那个我们没法自己算的antRiskToken, 靠token.js挂在app里hook. 另一个是拿到token之后, 从明文phone/password出发, 一步步把整个请求body在python里搓出来, 靠login.py. 中间那两次白盒AES调用python搞不定, 用unidbg起的/laes服务代理.

login.py

纯python脚本, 主流程按顺序:

1. 读token

--ant-risk-token没手动指定就调adb读文件, 只接受Tk9SSUQu开头的, 别的一律拒绝.

2. 两次MD5生成passwordArg和AES key

明文密码 -> 大写hex的passwordArg -> 再md5小写hex的AES key. 前面提到的两次MD5用途不同, 在这里落地.

3. 组装innerJson并AES加密得encryData

所有字段按key字典序排序, 序列化时用separators=(",", ":")去掉冒号后空格, 保证跟Java gson输出一致. aes_cbc_zero_iv_hex用python的cryptography库, AES/CBC/PKCS7, 16字节零IV, 输出大写hex.

4. 拼sign_plain并做特殊sha1

inner的字段全部保留, 再叠加外层字段, 排序, 拼&连接, 末尾追加&password=passwordArg.
byd_sha1按app规则实现:

format(b, "x")天然不补0, 单位数byte只输出一位hex, 完全对齐Java的Integer.toHexString. 偶数下标大写, 奇数下标小写. 这个跟标准hexdigest输出的长度都可能不一样, 直接标准sha1肯定过不了服务端校验.

5. 拼LoginParamsBean JSON

外层字段顺序也要跟真机trace一致, 因为下一步Add_Info追加字段的时候是按字符串拼接的, 顺序不同会导致checkcode的sha256完全不同. loginType是int, isAuto是string, 类型差一个都不行.

6. Add_Info追加字段和checkcode

add_json_pair就是模拟java里的字符串拼接版put, 处理了%要转义为%%的坑. checkcode先算再追加, 追加进去的checkcode不参与自己那次sha256.

7. 调两次/laes做白盒AES

两次结构一模一样, 只是key换了. 第一层拿完整的Add_Info明文, 输出c1, 第二层输入是c1 + StrIv1, 输出就是最终body.
pre_data_in_160 / pre_data_out_160 / pre_iv_160就是前面Nd.a那三个bit swap函数:

数据进laes前先preDataIn(bit swap + 0x44 XOR), iv进去前先preIv(纯bit swap), 拿到返回值再preDataOut(纯bit swap), 才是能base64的原始密文. 少任何一步, 得到的都是被混淆过的乱码, 服务端解不出来.

call_laes就是普通http POST, base64 encode入参, 收到base64 decode出结果:

http://127.0.0.1:18080/laes就是unidbg那边起的服务, 里面加载的是app原版的libwbsk_crypto_tool.so, 直接调用com.wbsk.CryptoTool.laesEncryptByteArr. 相当于是把app里的加密函数远程借用一下.
