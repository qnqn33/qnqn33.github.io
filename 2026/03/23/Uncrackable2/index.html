这里我的algorithmAidePro，也就是算法助手Pro发生了空指针异常，不过好像不重要，我把它关掉也依然会闪退。

这里应该是最核心的原因了libbinder ProcessState can not be used after fork，似乎是fork函数出了什么问题，那我们去libfoo.so里面看看怎么个事

MainActivity_init 里面会调用这个，简单来说就是父进程创建一个子进程一个自己的线程，子进程调试并监控父进程，线程监控子进程。

  • 一来子进程调试父进程，可以避免父进程被调试（因为在 Linux/Android 系统中，一个进程同一时刻只能被 一个 调试器通过 ptrace 附加（Attach）
  • 二来父子互相监控，一旦其中一个停止了，另外一个直接自杀

错误原因

然后经过ai的解析，我大致明白了崩溃的原因，现在用自己的话讲一遍

  • ptrace
    Linux 内核有个安全模块叫 Yama，它控制谁能 ptrace 谁。Android 高版本默认设置：


根据这一点，子进程在ptrace的时候会失败，那么子进程就不会进入那个无线的while循环去持续监控父进程，而是直接从最下面的return返回Java层，继续执行java层Init后面的代码

  • binder机制
    Binder 是 Android 的进程间通信（IPC）机制。每个 App 跑在自己的沙箱进程里，而显示窗口、启动 Activity、弹通知这些功能都在 system_server 进程里。App 想用这些功能，就必须通过 Binder 这条”管道”发消息给系统。

而创建子进程的时候，复制了父进程，但是pid二者还是不一样，这就导致内核的注册表没有子进程的记录，binder不会为子进程服务，当子进程需要binder的时候，就会报错

  • 两者结合
    子进程意外进入java层，java层检测到了root环境（不过我的sukisu怎么被检测出来了？），就会触发root detected的弹窗，这个过程就会用到binder。这时候binder发现子进程的pid不对，内核直接返回错误码。Java 层把它包装成了 RuntimeException。这里也对应了Caused by这个报错

第一次的 RuntimeException 触发了 UncaughtExceptionHandler，它试图通过 Binder 向系统报告”我崩溃了”：

这一次走到了 flattenBinder()，这里有个安卓15的专属机制
然后子进程被杀，根据前面的父子相互监视，父进程也自刎归天，程序闪退。

这段分析似乎没什么用，但是分析的过程还是很不错的。
